# Threat model

## System and assets

The system is a single-process Node/Express bank simulation with SQLite transaction state, a Redis-protocol nonce store, a browser bank UI, and an optional Socket.IO visualization dashboard. Assets are account balances, transaction history, session credentials, request integrity, and replay-detection state.

## Attacker cases

1. **Network observer without the signing secret.** The baseline attack traffic was generated by a script that holds the signing secret. That baseline script is a test driver, not an attacker capability. The modeled network attacker can observe and replay traffic, alter request fields, delay delivery, and reorder requests, but does not know the HMAC signing key.
2. **Leaked or compromised client key.** Anyone holding a client-side session key can forge correctly signed requests until the session expires. The session key is held in browser memory and is not protected from client compromise, browser extensions, injected scripts, or a user with developer tools. A leaked key bypasses HMAC authenticity; timestamp, nonce, request ID, account binding, and balance rules remain relevant.
3. **Legacy shared-secret mode.** `LEGACY_SHARED_SECRET=true` allows clients that know the configured server HMAC secret to use the legacy signature path. Anyone holding that shared secret can forge requests. The secret is not included in the new bank UI bundle.

## Trust assumptions

- Login PIN verification and session-key issuance happen on the simulation server. Session records and signing keys are stored server-side with a TTL.
- The account ID is bound to a user ID in SQLite. The transaction request must also match the authenticated session user.
- Redis or the selected nonce backend behaves according to the configured fail-open/fail-closed policy. The default research environment used Memurai Developer 4.2.3, not stock Redis.
- The simulated client and server are local. All reported latency is localhost latency and is not representative of a real network.
- The baseline traffic generator possessed the signing secret. The network attacker used for security interpretation does not.
- The stated network-attacker case assumes login and key delivery are protected by a trusted transport. This workspace defaults to HTTP, so a passive observer who captures the login response can learn the session key; the default deployment therefore does not meet that assumption and cannot support a production network-security claim.
- Experiment captures can set `PROXY_REDACT_LOGIN=true`. The recording proxy still forwards the login response unchanged to the browser, while its attacker-visible capture replaces both login request and response bodies with redaction markers. This models protected key delivery for the capture-based attacker; it does not add TLS or hide the response from a real on-path observer. The leaked-session-key case is measured separately as E1 scenario S9.

## Out of scope

Client compromise, malware, browser extension attacks, PIN phishing, credential stuffing, operator or telecom compromise, distributed multi-process deployment, production key management, denial of service, and real banking integrations are out of scope. The USSD-style gateway is a simulation and says nothing about any real operator or mobile financial service provider.
